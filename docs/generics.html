Generics

Parametric types and functions, monomorphized at compile time.

A type, fn, or impl declaration may carry a bracketed list of generic parameters. Each parameter is either a type parameter (T: type) or a value parameter (N: usize, or any other builtin scalar type) — a "const-generic" parameter, in the style of a C++ non-type template parameter. A declaration with generic parameters is never usable on its own; it must be instantiated with concrete arguments, either explicitly or, for functions, inferred from context. Every instantiation is compiled separately (monomorphization) — there's no runtime type erasure or boxing involved.

Declaring Generic Types

pub type List[T: type] = struct {
    allocator: Allocator
    data: *T
    length: usize
    capacity: usize
}

The generic_params clause follows the type's name and precedes =. Each parameter's declared type must be either the builtin type keyword (a type parameter) or one of the builtin scalar types — bool, an integer kind, or usize (a value parameter).

A generic type name alone is never a valid type
List by itself is a compile error naming the required arity — every use requires generic arguments in declared parameter order: List[i32], or Fixed[u8, 16] for a mixed parameter list. The one exception is inside the declaration's own body/signature — see "Implicit Self-Instantiation" below.

Declaring Generic Functions

// Const-generic: the parameter's declared type is a builtin scalar, not 'type' itself.
fn make_fixed[N: usize]() -> [N]u8 {
    mut buf: [N]u8 = default
    return buf
}

const b := make_fixed[16]()   // b: [16]u8

Inside the body and signature, each type parameter is a compile-time constant of type type, and each value parameter is a compile-time constant of its declared scalar type — usable anywhere a compile-time constant of that kind is legal: *T, size_of(T), a parameter's own : T, [N]u8, N * 2, a match/switch literal pattern, and so on. ext fn and macro declarations may not carry generic parameters — the grammar gives them no syntax position to write one. 

fn make_fixed[N: usize](fill: [N]u8 = default) -> [N]u8 { /* 'N' in the default is legal */ }

fn width[K: type](n := size_of(K)) -> usize { return n }

Default parameter values may reference the enclosing declaration's own generic parameters, type or value. This is the one exception to the rule that a default expression cannot reference another parameter of the same function — a default is re-resolved per instantiation, so size_of(K) above is 8 in width[i64]() and 4 in width[i32]().

Generic Impl Blocks

impl List[T: type] {
    pub fn reserve(self, min_capacity: usize) -> Allocator_Error {
        if min_capacity <= self.capacity {
            return_ok
        }
        const new_data_len := min_capacity * size_of(T)
        const new_data: *T = try self.allocator.realloc(self.data, new_data_len)
        self.data = new_data
        self.capacity = min_capacity
        return_ok
    }

    pub fn get(self, index: usize) -> (elem: T, List_Error) {
        if index >= self.length {
            return_err .Out_Of_Range
        }
        return_ok self.data[index]
    }
}

An impl block for a generic type is written once, against the unspecialized declaration, with its own generic-parameter clause immediately after the target type name — never against a concrete instantiation. The block's own parameter list must match the target type's declared arity exactly (matched by count, not by parameter kind or name). A method inside a generic impl block never declares its own generic parameters — its parameters are tied entirely to whichever concrete instantiation the enclosing block is applied to.

Per-instantiation specialization impls are not legal in v1
impl List[i32] { ... } (a body specific to just one instantiation) is a parse error — the bracket immediately after an impl target is always the block's own generic-parameter clause, never a set of concrete arguments. Always write impl List[T: type] { ... } once against the unspecialized declaration.

A generic struct may still implement a non-generic trait, once per concrete instantiation — traits themselves are not made generic (see Traits).

Type Parameters vs. Value Parameters

FormMeaningUsable as
T: typeType parameterA compile-time type constant — *T, size_of(T), a field/param's own : T, etc.
N: usizeValue parameterA compile-time constant of that scalar type — an array size [N]u8, an ordinary constant expression N * 2, a match/switch literal pattern.

A parameter list may freely mix both kinds, in any order — Fixed[T: type, N: usize]. A generic argument at an instantiation site is correspondingly either a type (for a T: type slot) or a compile-time constant expression of the matching scalar type (for an N: SomeScalar slot), checked the same way any other compile-time-constant expression is checked elsewhere in the language (e.g. an array-size expression).

Explicit vs. Inferred Instantiation

const a := make_list[i32]()   // explicit

const typed: List[i32] = make_list()   // T inferred from the declared type

mut buf: [16]u8 = make_fixed()      // N inferred from the expected array size

A generic function call accepts explicit arguments, or infers them — with or without an empty trailing []. Type parameters infer by unifying the parameter's declared type against an actual argument's static type wherever that parameter appears literally as a parameter's own : T in the signature, or (failing that) from the call's own expected-type context. Value parameters infer only from expected-type context — there's generally no argument shape to unify a value parameter against. If any parameter remains unbound after both passes, it's a compile error naming the specific unresolved parameter.

Generic Functions as Values

type Hash_Function[T: type] = fn(T) -> u64

fn fnv1a[T: type](value: T) -> u64 { /* ... */ }

const h: Hash_Function[i32] = fnv1a[i32]   // fn(i32) -> u64
const g := fnv1a[i64]                      // decays; g is 'fn(i64) -> u64'

A generic function instantiation can be used as a value, not just as a call callee: f[Args] in value position names that one monomorphized instantiation and has its function-pointer type. Generic arguments must be written explicitly — the inference above draws on a call's arguments and expected type, and in value position there are none, so a bare generic function name is an error ("supply its generic arguments to name a specific instantiation").

The ordinary function-pointer rules apply unchanged to the instantiation: a variadic generic function's address still can't be taken, and @always_inline still warns. This is also the only way to name an instantiation as a value, since instantiations are otherwise observable only through their mangled symbol names.

Implicit Self-Instantiation

pub fn make_list[T: type](allocator := heap_allocator()) -> List {
    // '-> List' here is sugar for '-> List[T]'
    return { .allocator = allocator, .data = nil, .length = 0, .capacity = 0 }
}

Inside a declaration whose own generic-parameter list has arity N, a bare reference to a generic name — including a self-reference to the enclosing declaration itself — is sugar for applying the enclosing declaration's own parameters, in order, provided the referenced name's own arity is also N (matched by count, not by parameter kind or name). Inside impl List[T: type] { ... }, a bare List or T likewise resolves against the impl's own binding. Explicit brackets are always still accepted — implicit self-instantiation only applies to a bare reference with no brackets written at all.

Monomorphization and Type Identity

Name[Args] for a fixed declaration and a fixed, value-equal argument tuple denotes exactly one concrete instantiation program-wide — every occurrence of List[i32] anywhere in the program refers to the same underlying type. This is nominal per declaration, not deep structural interning across different declarations: two different generic declarations instantiated with identical arguments and identical resulting layouts are still two different, mutually non-assignable types — the same rule ordinary non-generic named types already follow.

Codegen generates an instantiation only when it's actually reachable from a live call or type use, the same "unselected branch never visited" posture when uses for dead branches — except stricter: an unreached generic instantiation is never type-checked at all in v1, not merely never emitted (see "No Bounds in v1" below).

Coherence

impl TRAIT for List[T: type] { ... } is written once against the unspecialized declaration and governs every concrete instantiation of List. The same single-impl-per-(TRAIT, TYPE) coherence rule traits use elsewhere applies at this unspecialized level: at most one such impl exists anywhere in the program, and it must live in the module that defines the trait or the module that defines List itself.

No Bounds in v1

Generic parameters are unconstrained
There is no way in v1 to declare that a type parameter must implement a given trait, or that a value parameter must satisfy some predicate. An operation a given instantiation's body can't actually support is only caught when that specific instantiation is generated and checked — not at the generic declaration's own point of definition. This is a real departure from the "both branches always type-checked" posture the rest of the language uses for when: a generic body that's never instantiated is never checked at all, not merely never emitted.

Full Example

pub type Fixed[T: type, N: usize] = struct {
    data: [N]T
}

impl Fixed[T: type, N: usize] {
    pub fn sum(self) -> T {
        mut total: T = default
        for v in self.data {
            total += v
        }
        return total
    }
}

pub fn main() {
    const nums: Fixed[i32, 4] = { .data = {1, 2, 3, 4} }
    printf("sum = %d\n", nums.sum())
}
// Output:
// sum = 10
