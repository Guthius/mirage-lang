Traits

Dynamic dispatch through lightweight trait handles.

Mirage has no generics. When you need one function to work over several unrelated types — without a big switch over every possibility — traits give you that, through runtime dynamic dispatch. If you've used Go's interfaces or Rust's dyn Trait, this will feel familiar: a trait is a set of method signatures, and any type that implements all of them can be used wherever that trait is expected.

Declaring a Trait

A trait is declared like any other named type, using trait { ... } as the type expression. Its body lists method signatures only — fn declarations with self or mut self as the first parameter, no body: 

type Drawable = trait {
    fn draw(self)
    fn area(self) -> f64
}

A trait must declare at least one method — an empty trait {} is a compile error.

What Drawable means as a type
Using Drawable as a variable's, field's, or parameter's type works exactly like you'd expect from Go or Rust's dyn Trait: it means "any value that implements Drawable", and the compiler enforces that — only a pointer to a type with an impl Drawable for ... can go there. Under the hood, that's represented as a handle: a fixed-size, 16-byte fat pointer (a data pointer plus a vtable pointer), the same 16 bytes regardless of which trait it names. That representation detail is why only a pointer coerces to it (see below) and why handles can't cross an ext fn boundary — but day to day, just think of Drawable as "a Drawable object."

Implementing a Trait

Use impl TRAIT for TYPE to implement a trait for a concrete struct, enum, or union type: 

type Circle = struct {
    x: f64
    y: f64
    radius: f64
}

impl Drawable for Circle {
    fn draw(self) {
        printf("circle at (%.1f, %.1f)\n", self.x, self.y)
    }
    fn area(self) -> f64 {
        return self.radius * self.radius * 3.14159
    }
}

type Square = struct {
    x: f64
    y: f64
    side: f64
}

impl Drawable for Square {
    fn draw(self) {
        printf("square at (%.1f, %.1f)\n", self.x, self.y)
    }
    fn area(self) -> f64 {
        return self.side * self.side
    }
}

self inside a trait impl is a pointer to the concrete type, exactly like a bare impl TYPE { ... } block. Every method the trait declares must be implemented with an exactly matching signature (same name, same self/mut self, same parameter and return types) — and the impl block may not contain extra methods beyond the trait's own surface; put those in a separate bare impl TYPE { ... } instead.

Coherence Rules

  • impl TRAIT for TYPE is only legal in the module that defines the trait, or the module that defines the type. Implementing someone else's trait for someone else's type ("orphan impl") is a compile error.
  • A given (TRAIT, TYPE) pair may be implemented at most once anywhere in the program.
  • A trait-impl method with the same name as an existing bare-impl method on the same type is an error, caught at the trait impl. Two different trait impls on the same type supplying a method of the same name is an error at the second one.

These rules are all checked at declaration time, so a program that compiles is guaranteed to have no ambiguity about which method a call resolves to.

Static vs. Dynamic Dispatch

Calling a trait method directly on a concrete value or a pointer to one is static dispatch — resolved entirely at compile time, no vtable involved: 

mut circle: Circle = {.x = 10.0, .y = 10.0, .radius = 5.0}
circle.draw()          // static dispatch: calls Circle's draw() directly

A pointer to a type that implements a trait automatically coerces to that trait's handle wherever an expected type is known — variable initializers, assignment, return statements, call arguments, struct and array field initializers: 

mut square: Square = {.x = 0.0, .y = 0.0, .side = 4.0}

// &circle and &square (pointers) coerce to Drawable handles here
mut shapes: [2]Drawable = { &circle, &square }

for shape in shapes {
    shape.draw()        // dynamic dispatch: resolved through the handle's vtable at runtime
    printf("area = %.2f\n", shape.area())
}

This is dynamic dispatch: the call resolves against the trait's method list and jumps through the handle's vtable at runtime, so the loop above doesn't need to know whether each element is a Circle or a Square. Static and dynamic dispatch ultimately call the exact same underlying function — the vtable only exists so the call site doesn't need to know the concrete type.

Only a pointer coerces to a handle — coercing a bare (non-pointer) value is a compile error, as is coercing a pointer to a type that doesn't implement the trait. And it only works one way: once a concrete pointer has become a handle, there is no downcasting back to the concrete type or pointer.

try and multi-return through a handle
Calling a fallible trait method through a handle works exactly like a fallible free-function call — try propagates the same way whether the call is static or dynamic. A multi-return trait method can be captured with a group declaration through a handle too.

Handle Values

ValueMeaning
nilAssignable to a handle — both the data pointer and vtable pointer are zero.
defaultSame as nil for a handle type.
undefinedLegal — uninitialized storage, no zeroing.
Calling through a nil handle is undefined behavior
No runtime check is emitted for a nil handle — calling a method on one will crash. If a handle might be nil, compare it against nil first.

A handle supports no field access, no dereference, and no arithmetic. The only comparisons allowed are == and != against nil — comparing two non-nil handles for equality, or any relational operator, is a compile error. Otherwise, handles round-trip like any other 16-byte value: struct fields, function parameters, return values, and array/slice elements all work with no special handling.

Not usable in ext fn signatures
A handle has no C ABI representation, so it cannot appear as an ext fn parameter or return type.

Full Example

ext fn printf(fmt: *u8, ...) -> i32

type Drawable = trait {
    fn draw(self)
}

type Circle = struct { radius: f64 }

impl Drawable for Circle {
    fn draw(self) {
        printf("○ radius=%.1f\n", self.radius)
    }
}

type Square = struct { side: f64 }

impl Drawable for Square {
    fn draw(self) {
        printf("□ side=%.1f\n", self.side)
    }
}

pub fn main() {
    mut c: Circle = {.radius = 2.0}
    mut s: Square = {.side = 3.0}

    const shapes: [2]Drawable = { &c, &s }
    for shape in shapes {
        shape.draw()
    }
}
// Output:
// ○ radius=2.0
// □ side=3.0
