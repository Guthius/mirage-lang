Declaration Attributes

Compiler-recognized metadata attached to a function: @naked, @no_return, @always_inline, @section("..."), and @init.

An @name attribute clause may precede a fn declaration, attaching compiler-recognized behavior to it — suppressing the prologue/epilogue, forcing inlining, placing it in a specific ELF section, or marking it as a module initializer. Attributes are currently legal only on module-scope fn declarations — not ext fn, not methods inside an impl block.

the attribute comes first
If a declaration is both pub and attributed, the attribute precedes pub: 
@naked
pub fn raw_entry() {
    asm { ret }
}
Never pub @naked fn ... — that order is a parse error.

Syntax

@naked                        // single — no arguments
@(naked, no_return)           // grouped — two or more, no arguments
@section(".text.init")        // single — with an argument

Only one attribute clause may precede a declaration. Two separate clauses on the same declaration are a parse error: 

// error: expected declaration, got '@'
@naked @no_return
fn f() { }

Use the grouped form instead, which accepts one or more names:

@(naked, no_return)   // legal — a single grouped clause
fn f() { asm { ret } }

A grouped-form member never takes its own argument list — only the ungrouped @name(args) form takes arguments: 

// error: a grouped attribute ('@(...)') cannot take arguments;
// use the single '@name(args)' form instead
@(section(".text"))
fn f() { }

Known Attributes

no_return, naked, always_inline, section, and init are the only recognized names. Anything else is a sema error: 

error: unknown attribute '@foo'. Known attributes: no_return, naked, always_inline, section, init.

@no_return

Declares that the function never returns control to its caller — it loops forever, calls a process-exit primitive, panics, etc. The prologue/epilogue are unaffected; the only difference is codegen marking the function (and every call to it) LLVM noreturn, letting LLVM omit the unreachable successor block after a call.

A @no_return function whose return type is neither void nor error(...) still compiles — but produces a warning, since the value can never actually be returned: 

warning: a '@no_return' function with a value return type will never return its value

@naked

Suppresses the compiler-generated prologue and epilogue entirely: no stack frame setup, no callee-saved register preservation, no implicit ret. The function body is expected to handle all of that itself, typically via inline asm. 

@naked
fn raw() {
    asm {
        ret
    }
}

If the body contains any statement other than an asm { ... } block, a warning (not an error — the function still compiles) is emitted, since a naked function's non-asm code implicitly assumes a valid stack frame the compiler never set up: 

warning: '@naked' function contains a non-'asm' statement; naked functions should contain
         only inline 'asm' blocks, since the compiler emits no prologue/epilogue for them

@always_inline

Requests that the function be inlined at every direct call site (LLVM's alwaysinline). If the function's address is ever taken — assigned to a function-pointer-typed variable, passed as a callback, returned — a warning is emitted, since calls made through that pointer can't be inlined: 

@always_inline
fn add(a: i32, b: i32) -> i32 {
    return a + b
}

pub fn main() {
    const fp: fn(i32, i32) -> i32 = add
    // warning: taking the address of '@always_inline' function 'add'. ...
}

The function still exists as an ordinary callable symbol — only indirect calls through the pointer lose the inlining; @always_inline has no effect on them.

@section("name")

Places the function in the named ELF section instead of the default .text. The argument must be a non-empty compile-time-constant []u8 string: 

@section(".text.boot")
fn boot_entry() {
    asm { ret }
}

An empty string is a sema error:

error: '@section' argument must not be an empty string

The section name is passed to the linker verbatim — Mirage does not validate ELF section naming conventions itself.

@init

Marks the function as a module initializer, automatically called once before main (hosted builds) or via the generated _init (freestanding builds — see below). 

@init
fn setup() {
    // runs once, before main — no 'pub' needed
}

Restrictions

  • Must take no parameters.
  • Must return nothing or error(SomeEnum) — any other return type is a sema error.
  • Is not allowed on a method inside an impl block:
error: '@init' is not allowed on impl methods; declare a module-scope function instead

A module may declare more than one @init function; same-module @init functions always run in source declaration order. Unlike ordinary functions, @init does not need to be pub — the generated _init is emitted into the same compilation as every other function in the program, so it can call a private @init function directly. The common case is the opposite of pub: a module's initializer usually has no business being an ordinary externally-callable symbol at all.

Cross-Module Ordering

If one module's @init function references a symbol — a variable read/write, or a function call — declared in another module, that other module's @init function(s), if any, are guaranteed to run first: 

// b/main.mir
pub mut ready := false

@init
fn setup_b() {
    ready = true
}

// main.mir — depends on b, so setup_b() is guaranteed to run first
const b := import("b")

@init
fn setup_a() {
    assert(b.ready)   // always true
}

This dependency graph is built from actual symbol references made in @init function bodies, not merely the import graph — an @init function that never touches a given imported module doesn't create an ordering dependency on it. A cycle in this graph is a sema error naming both modules: 

error: circular '@init' dependency: module 'A' requires module 'B' to initialize first, but
       'B' also (transitively) requires 'A' to initialize first

Failure Handling

If an @init function returns a non-Ok error(...), the process immediately terminates with exit code 1 — a fixed sentinel, not the raw error value (which has no defined integer representation outside the function's own context) — and main never runs: 

type InitError = enum { Failed }

@init
fn setup() -> error(InitError) {
    return_err .Failed
}

Generated _init and --noinit

The compiler synthesizes a function named _init that calls every @init function across the program in the order described above. In hosted builds, _init is called from the generated _start, before main.

Freestanding builds
_init is still generated with --freestanding, but (as always) no _start is synthesized — the user's own _start is responsible for calling _init itself, at whatever point is appropriate.

Passing --noinit to the driver skips generating _init entirely (and, in hosted builds, the _start call to it). Every @init function still compiles normally and remains individually callable — only the automatic invocation is suppressed.

Conflicting Attributes

Some combinations are rejected outright, each with its own diagnostic:

CombinationWhy
@naked + @always_inlinea naked function has no compiler-generated body shape to inline
@init + @nakedinit functions must be callable normally, from the generated _init
@init + @no_returnan initializer must return control so the next one can run
@init + @always_inlineinit functions are called once, from generated code — inlining defeats the purpose
