Inline Assembly

Raw x86-64 assembly inside a function body, for the rare case where no ext fn wrapper exists — like issuing a syscall directly.

An asm { ... } block embeds raw x86-64 assembly, written in Intel syntax, directly inside a function. It's an escape hatch: most programs never need it, but it's there for the handful of cases — issuing a syscall with no libc wrapper, reading a specific register — that no amount of ordinary Mirage code can express.

Function bodies only
asm { ... } is legal only inside a function body. Writing one at module scope is a compile error: 
error: asm blocks are only legal inside function bodies

A First Example

One instruction per line, mnemonic first, then zero or more comma-separated operands. Mirage variables can be read by value or written through their address: 

pub fn add_one(x: i32) -> i32 {
    mut result: i32 = undefined
    asm {
        mov eax, x
        add eax, 1
        mov &result, eax
    }
    return result
}

x (read by value) and &result (written through its address) are Mirage variables; eax is a raw register; 1 is an immediate. The lexer captures everything between the outer { } as raw text — it is never tokenized as Mirage code, so mnemonics, registers, and comments inside an asm block follow their own rules, described below.

Operands

Each operand in an instruction is one of four forms:

FormMeaning
eaxA register (see the table below).
42, -5, 0x2aA decimal or hexadecimal integer immediate. Float immediates aren't supported.
flagsA Mirage variable, read by its current value.
&fdA Mirage variable's address — & immediately followed by an identifier, no space — letting the instruction write through it.

Only scalar and pointer-typed variables can appear as operands — a struct, array, or slice is a compile error. const and mut bindings both work as &var targets: taking a binding's address and writing through it is always legal in Mirage, regardless of how the binding itself was declared. An unrecognized variable name is a compile error: 

error: unknown identifier 'fd' in asm block.

; and # both start a comment running to the end of the line.

Registers

All 64-bit general-purpose registers are available, at every width. Register names are case-insensitive. Each one belongs to a family — its 64-bit root (e.g. eax's family is rax) — which matters for clobber tracking below: writing to any width of a register clobbers the whole family.

WidthRegisters
64-bitrax rbx rcx rdx rdi rsi rsp rbp r8–r15
32-biteax ebx ecx edx edi esi esp ebp r8d–r15d
16-bitax bx cx dx di si sp bp r8w–r15w
8-bital bl cl dl dil sil spl bpl r8b–r15b
Not supported in v1
SSE/AVX/FPU registers (xmm0, ymm0, st0, ...), segment registers (cs, ds, ...), control/debug registers (cr0, dr0, ...), and memory operands with displacement/scale syntax ([rax + 8]) are all recognized — so they produce a clear "not supported in v1" error — rather than being silently misread as a Mirage variable name. Labels/local jumps, string operands, and float immediates are also out of scope for v1.

Operand Direction and Clobbers

The compiler needs to know which operands an instruction reads versus writes, so it can tell the surrounding function's own register allocator which registers the block disturbs. It looks this up per mnemonic, in two tiers:

Mnemonic(s)Reads / Writes
mov, leaWrite, Read
movzxWrite, Read — widths may differ; see below
add, sub, and, or, xorRead/Write, Read
not, neg, inc, decRead/Write
cmp, testRead, Read
pushRead
popWrite
nop, ret, syscall(no operands)
jmp, je, jne, jl, jg, ... (all conditional jumps)Read
callRead

A mnemonic outside this table isn't a compile error — it's passed straight through to the assembler, with a conservative guess (first operand read/write, the rest read) and a warning: 

warning: unknown mnemonic 'cpuid' — assuming first operand is read/write
         and remaining operands are read. Verify clobbers manually.

Some instructions also touch registers that never appear in their operand list at all:

  • syscall reads rax, rdi, rsi, rdx, r10, r8, r9; clobbers rax (the return value), rcx, r11 (destroyed by the kernel).
  • call clobbers every System V caller-saved register: rax rcx rdx rsi rdi r8 r9 r10 r11.
  • div/idiv read rdx:rax and write rax (quotient) / rdx (remainder).
  • mul/imul, in their one-operand form, read and write rdx:rax.

Every register an instruction writes, plus its implicit clobbers, plus a memory clobber whenever any &var operand appears anywhere in the block, all feed the compiler's own register allocator — this is what keeps it from putting one of its own values in a register your asm block is about to overwrite.

Width Checking

Where a register and a Mirage variable operand appear together in one instruction, their widths normally have to match:

Mirage typeRegister width
i8 / u88-bit
i16 / u1616-bit
i32 / u3232-bit
i64 / u64 / usize / any pointer / anyptr64-bit

A mismatch is a warning, and it names the fix:

warning: asm operand 'fd' has type 'i32' (32 bits) but register 'rax' is
         64 bits. Consider using 'eax' instead.
This warning isn't just cosmetic
In Intel syntax with no explicit size specifier, the assembler infers a memory write's size from the register's width. mov &fd, rax where fd is i32 writes all 8 bytes of rax into a 4-byte stack slot — silently corrupting whatever sits next to it. The same applies to a by-value operand: mov rsi, flags with an i32 flags doesn't just warn, it fails to assemble outright, because the loaded value is sized to flags's own type and a mismatched register name next to it produces an invalid instruction. Use esi, not rsi.
movzx is the one exception
Zero-extending a narrower source into a wider destination is movzx's entire purpose, so its two operands are supposed to differ in width — it's exempt from the warning above. Instead it enforces its own real x86 constraints as compile errors:
  • The source must be 8 or 16 bits — there's no movzx encoding for a 32- or 64-bit source. Writing a 32-bit register already zero-extends its parent 64-bit register for free, so a plain mov (into the matching 32-bit sub-register, e.g. esi not rsi) is what to use for an i32 value — not movzx: 
    error: 'movzx' source must be 8 or 16 bits (got 32 bits) — there is no
       'movzx' encoding for a 32-bit or 64-bit source; use 'mov' instead,
       which already zero-extends automatically when writing a 32-bit
       register
  • The destination must be strictly wider than the source: 
    error: 'movzx' destination width (32 bits) must be wider than source
       width (32 bits)
asm {
    movzx eax, byte_value   # byte_value: u8 -> zero-extended into eax
}

Asm Expression

Everything above is asm { ... } as a statement — useful for side effects (&var writes) but unable to produce a value directly. A second, expression form additionally names an output register whose value at block-exit becomes the expression's value: 

asm -> eax { ... }              # result type inferred from context
asm -> eax: i32 { ... }         # result type explicit

Unlike the statement form, asm -> reg [: type] { ... } is a normal expression: legal anywhere an expression is legal — return, a variable declaration's initializer, a function-call argument, and so on — not just as a bare statement. Its instruction body uses exactly the same grammar (registers, immediates, Mirage variable operands, operand-direction analysis, clobbers, movzx's exception, width checking) as the statement form above; only the header (-> reg [: type]) is new. 

pub fn open(filename: *u8, flags: i32, mode: i32) -> i32 {
    return asm -> eax {
        mov rax, 2
        mov rdi, filename
        mov esi, flags
        mov edx, mode
        syscall
    }
}

Result type inference. When : type is written explicitly, that is the result type, full stop. Otherwise the result type is inferred from the surrounding expected-type context — a return statement's declared return type, a variable declaration's declared type, and so on. If neither an explicit : type nor an expected-type context is available, it's a sema error: 

error: cannot infer result type for 'asm -> eax'; add an explicit type
       annotation: 'asm -> eax: i32 { ... }' or annotate the variable
       receiving the result.

Result register width checking compares the result register's width against the resolved result type's width, using the same table as ordinary operand width checking above. A mismatch is a warning, naming a same-family register of the correct width as the fix: 

warning: asm result register 'rax' is 64 bits but result type 'i32' is 32
         bits. Consider using 'eax' to avoid implicit truncation.
The result register is always an implicit clobber
Its family is added to the clobber set even when no instruction in the block explicitly writes it — the surrounding code cannot assume the register's prior value survives an asm -> reg block, whether or not the body's own instructions happened to touch it.

Composes with &var writes. The register-return mechanism and &var memory writes are completely independent and may be used together in the same block: 

mut status: i32 = undefined
const result: i32 = asm -> eax {
    mov eax, 42
    mov &status, eax   # a second, independent output
}

Full Example

Issuing the Linux open syscall directly, with no ext fn wrapper. filename is a 64-bit pointer, so rdi is correct as-is — flags and mode are i32, so they need the matching 32-bit registers, esi/edx, not rsi/rdx: 

ext fn printf(fmt: *u8, ...) -> i32

pub fn open(filename: *u8, flags: i32, mode: i32) -> i32 {
    mut fd: i32 = undefined
    asm {
        mov rax, 2            # syscall number for open()
        mov rdi, filename
        mov esi, flags
        mov edx, mode
        syscall
        mov &fd, eax        # eax, not rax: fd is i32
    }
    return fd
}

pub fn main() -> i32 {
    const fd: i32 = open("/dev/null", 0, 0)
    if fd < 0 {
        printf("open failed: fd=%d\n", fd)
        return 1
    }
    printf("open succeeded: fd=%d\n", fd)
    return 0
}
# Output:
# open succeeded: fd=3
