Error Handling

Typed error(T) unions, try propagation, typestate checking, and defer cleanup.

Mirage has no exceptions and no single built-in "error code" type. Instead, a function that can fail says exactly what it can fail with, using an ordinary enum or tagged union wrapped in error(...). The compiler then tracks, at compile time, whether you've actually handled that failure before letting the value out of scope.

Declaring Error Types

Any enum(i32) or union(enum) type becomes usable as an error the moment you reference it inside error(...) — there's no special keyword or attribute needed: 

type ParseError = enum(i32) {
    InvalidNumber = 1
    UnexpectedEnd = 2
}

type IoError = union(enum) {
    NotFound:         []u8   // carries the path that wasn't found
    PermissionDenied            // no payload
}

Any variant value is allowed, including 0 — success vs. failure is tracked by a separate hidden tag, not by convention over the payload value. An enum(i32) used as an error type must declare i32 as its underlying type explicitly.

Fallible Functions

A function is fallible when its last return type is error(T) (one error type) or error(A | B | C) (a union of several). Any other return values come first: 

fn parse_int(text: []u8) -> (i32, error(ParseError)) {
    if len(text) == 0 {
        return_err .UnexpectedEnd
    }
    // ... parsing logic ...
    return_ok 42
}

// A void-return fallible function still needs the parentheses-free single type
fn validate(text: []u8) -> error(ParseError) {
    if len(text) == 0 { return_err .UnexpectedEnd }
    return_ok
}

// A function that can fail two different ways
fn load_setting(path: []u8) -> (i32, error(ParseError | IoError)) {
    // ...
    return_ok 0
}

error(A | A) (a duplicate member) is rejected at compile time. Member order is cosmetic — error(A | B) and error(B | A) name the same type.

What's really being returned?
The compiler generates a hidden tagged union for every distinct error(...) spelling: an outer Ok / Failed tag, where Failed carries the payload (your error type, or — for a union — a second tag dispatching on which member occurred). This generated type has no user-visible fields; you only ever interact with it through return_ok/return_err, boolean checks, try, and match/switch — never by reading a tag or payload directly.

return_ok and return_err

These are sugar over return for fallible functions. Both run deferred statements first, exactly like a normal return. 

return_err .Variant                     // payload-free variant
return_err .Variant(payload)             // single non-struct payload (sugar)
return_err TypeName.Variant{.field = value}  // fully-qualified, for disambiguation

return_ok value1, value2       // non-error return values, in order
return_ok                       // bare — for an error-only return type

The unqualified .Variant form works as long as that variant's name is unique across all of the function's declared error member types; if two member types both declare a variant with the same name, qualify it as TypeName.Variant{...} (only variants with a payload support the qualified form — rename an ambiguous payload-free variant instead).

re-propagating a captured error
return_err's operand isn't limited to a fresh .Variant construction — it also accepts an expression that already evaluates to a compatible error value: a plain value of one of the function's error member types, or a captured error(...) value (this function's own, or one whose member types are a subset of it, the same rule try uses). This is the natural way to re-propagate an error you already captured from a group declaration, and unlike a plain return it works even when the function has other non-error return values, since return_err leaves those slots undefined for you: 
const n, err := parse_int(text)
if err {
    return_err err       // re-propagate the captured error as-is
}

Capturing Fallible Results

A fallible call's result must be captured, propagated with try, or explicitly discarded with _ — leaving it untouched is a compile error: 

parse_int(text)                        // error: ignored error result
const n, _ := parse_int(text)          // ok: explicitly discarded
const n := try parse_int(text)         // ok: propagated
const n, err := parse_int(text)        // ok: captured

Unless the error is marked ignorable — see below.

Ignorable Errors (?)

Some failures are fatal for essentially every caller. Forcing an if err after every allocation buys nothing but noise. Prefixing a function's last return type with ? marks its error as ignorable: callers may leave it unhandled, and the compiler synthesizes the check they didn't write. 

pub type Allocator = trait {
    fn alloc(self, size: usize, zero_memory := true) -> (anyptr, ?Allocator_Error)
    fn realloc(self, ptr: anyptr, size: usize) -> (anyptr, ?Allocator_Error)
    fn free(self, ptr: anyptr)
}

?T, where T is an enum(i32) or union(enum), is sugar for ?error(T). The explicit ?error(A | B) form and an alias to an existing error type (?SomeIoError) work too. ? is legal on free functions, impl methods, trait methods, and function-pointer types — but only on the last return type, the one a call site can drop. Anywhere else (an earlier return slot, a parameter, a field, a variable annotation, a type alias) it is a compile error, as is ? on a type that isn't an error type.

Leaving an ignorable error unbound emits a check on it. On failure the program prints the failing variant's name and the call's source location to stderr and exits with status 101: 

panic: unhandled Allocator_Error.Out_Of_Memory at main.mir:3:23

The slot may be dropped in any single-value context, and in a group declaration written one name short of the arity: 

allocator.alloc(n)                 // ok: statement, both values dropped
const ptr := allocator.alloc(n)    // ok: error dropped, checked
foo(allocator.alloc(n))            // ok: argument position
return allocator.alloc(n)          // ok: return position
const w, h := measure()            // ok: measure() -> (i32, i32, ?E)

Naming the slot — including naming it _ — is the deliberate opt-out and synthesizes no check. That is the escape hatch for the caller who really does mean "I don't care": 

const ptr, _ := allocator.alloc(n)    // silently ignored, no check
const ptr, err := allocator.alloc(n)  // handled explicitly, as usual
const ptr := try allocator.alloc(n)   // propagated, as usual

A function whose only return value is ?error(...) still yields that error in a value context — there would be nothing else to yield — so the drop applies to it only in statement position: 

touch(n)                 // ok: statement, dropped and checked
const e := touch(n)      // captured, exactly like a non-optional error
? is part of the type
error(E) and ?error(E) are distinct types: an impl must match its trait's marking, and two function-pointer types differing only in ? are different types. Because they hold identical values, though, assignment between them is free in both directions, and everything about handling an error already in hand — try, return_err, match/switch, boolean coercion, the subset rule — ignores the marking entirely. A value inferred from a ?-returning function carries it (const e := touch(n) has type ?error(E)), and reflection reports it as Type_Info.Error_Type.is_optional.

? on main or on an @init function is accepted but has no effect: neither has a caller that could drop anything, and both already terminate the process on failure.

Boolean Coercion

An error value used where a bool is expected (if, while, &&, ||, unary !, ternary condition) implicitly checks the hidden Ok/Failed tag: if err is true when err is Failed; if !err is true when it's Ok. 

const n, err := parse_int(text)
if err {
    printf("parse failed\n")
    return err
}
printf("parsed: %d\n", n)

Error State Tracking

The compiler tracks each error-typed local's state — Unknown (just captured), Failed, or Ok — as it flows through if/while branches: 

const n, err := parse_int(text)
if err {
    // err is known Failed here
} else {
    // err is known Ok here
}

Early-return narrowing: after if !err { ... } where the body unconditionally exits (return/return_ok/return_err/ break/continue on every path) and there's no else, err is narrowed to Failed for the rest of the enclosing scope: 

const n, err := parse_int(text)
if !err { return_ok n }
// err is known Failed here — a match on it below is legal
Redundant checks are flagged
Checking an error variable again once its state is already known (e.g. two if err checks in a row with nothing resetting it in between) produces a compiler warning. Reassigning a mut error variable, or taking its address with &, resets its state back to Unknown.

match / switch on Error Values

You can only match/switch on an error value once it's known Failed (narrow it first, as above) — matching on an Unknown-state error is a compile error. The match is transparent: you match directly against your own variant names, never against the hidden Ok/Failed wrapper. For an error union, match first dispatches on which member type occurred, typically via a nested match on that member's own variants: 

fn describe(err: error(ParseError | IoError)) {
    if err {
        match err {
            .ParseError(e): match e {
                .InvalidNumber: printf("invalid number\n"),
                .UnexpectedEnd: printf("unexpected end of input\n")
            },
            .IoError(e): match e {
                .NotFound(path): printf("not found: %s\n", path),
                .PermissionDenied: printf("permission denied\n")
            }
        }
    }
}

Exhaustiveness follows the same rules as any tagged-union/enum match (see Control Flow): every member type and every one of its variants must be covered, or end with a _ default arm.

The try Expression

try calls a fallible function and, if it failed, immediately propagates that failure out of the enclosing function — running deferred statements first — instead of returning to the caller normally. On success, it evaluates to the non-error return value(s). 

fn read_config_value(text: []u8) -> (i32, error(ParseError)) {
    // If parse_int fails, propagate its error immediately
    const n: i32 = try parse_int(text)
    return_ok n * 2
}

try requires the callee's error(...) type to be a subset of (or equal to) the caller's own declared error(...) — every error member type the callee can produce must also be one the caller declares: 

// OK: caller's error union (ParseError | IoError) is a superset of
// parse_int's (ParseError) and open_file's (IoError)
fn load_setting(path: []u8) -> (i32, error(ParseError | IoError)) {
    const handle := try open_file(path)   // open_file -> error(IoError)
    defer close_file(handle)

    const text := read_all(handle)
    const n := try parse_int(text)          // parse_int -> error(ParseError)
    return_ok n
}

try Precedence

try binds tighter than binary operators:

// try applies only to f(x), not to the entire expression
try f(x) + g()    // same as: (try f(x)) + g()

// Parentheses to chain member access after try:
const s := (try lookup(key)).size

The defer Statement

defer registers a statement to run when the enclosing block exits — whether by fall-through, return, break, or continue. 

fn with_resource() -> error(IoError) {
    const handle := open("file.txt")
    defer close(handle)   // always runs on exit

    try read(handle)      // defer still runs if this propagates
    return_ok
}

LIFO Order

Multiple defers in the same scope run in last-in, first-out order (like a stack unwind):

fn lifo_demo() {
    defer printf("first registered\n")
    defer printf("second registered\n")
    defer printf("third registered\n")
}
// Output:
// third registered
// second registered
// first registered

Defer in Nested Blocks

Each block has its own defer scope. Inner-block defers fire when that block exits:

fn block_defer() {
    {
        defer printf("inner\n")    // fires when inner block exits
    }
    printf("outer\n")              // runs after inner defer
}
// Output:
// inner
// outer

Defer in Loops

A defer inside a loop body fires on every iteration, including on break:

mut i: i32 = 0
while i < 3 {
    defer printf("tick\n")   // prints "tick" once per iteration
    i++
}
// Output: tick tick tick

Defer and Early Return

Defers run even on early return. Return values are captured before defers execute:

fn example() -> i32 {
    defer printf("cleanup\n")
    if some_condition {
        return 1   // defer fires before the ret instruction
    }
    return 0
}

Defer Restrictions

  • Using try inside a defer body is a compile error.
  • return, break, or continue that escape the defer body are compile errors.

Defer + Try Together

When try propagates a failure, every deferred statement accumulated up to that point in the function runs before the function actually returns — in LIFO order — enabling reliable cleanup even on error paths: 

fn acquire_and_process() -> error(IoError) {
    const a := try acquire_resource_a()
    defer release_resource_a(a)

    const b := try acquire_resource_b()
    defer release_resource_b(b)

    // If this fails, both release_b and release_a run (LIFO), then the error propagates
    try do_work(a, b)

    return_ok
}

Errors at Entry Points

error(T) can be the return type of main. Ok exits with code 0; Failed exits with code 1: 

pub fn main() -> error(ParseError | IoError) {
    try run_app()
    return_ok
}

Full Example

ext fn printf(fmt: *u8, ...) -> i32

type ParseError = enum(i32) {
    InvalidNumber = 1
    UnexpectedEnd = 2
}

fn parse_digit(c: u8) -> (i32, error(ParseError)) {
    if c < '0' || c > '9' {
        return_err .InvalidNumber
    }
    return_ok cast(c - '0', i32)
}

fn sum_digits(text: []u8) -> (i32, error(ParseError)) {
    mut total: i32 = 0
    for c in text {
        // try propagates a bad digit straight out of sum_digits
        total += try parse_digit(c)
    }
    return_ok total
}

pub fn main() -> error(ParseError) {
    const total, err := sum_digits("1234")
    if err {
        printf("parse failed\n")
        return err
    }
    printf("sum = %d\n", total)   // sum = 10
    return_ok
}
